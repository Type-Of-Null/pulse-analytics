# ADR-0001: Kafka как буфер между приёмом и хранилищем

**Статус:** принято

## Контекст
Клиентские SDK шлют события пиками (релизы, рассылки). ClickHouse плохо переносит много мелких
INSERT'ов (каждый создаёт part, растёт фон merge'ей, `Too many parts`), а при его недоступности
приём событий не должен падать.

## Решение
`ingest-api` только валидирует и пишет в Kafka (`events.raw`), запись в ClickHouse делает отдельный
`writer` крупными батчами (до 5000 строк / 1 с).

- Продюсер идемпотентный (`enable_idempotence`, `acks=all`), сжатие LZ4, linger 5 мс.
- Ключ партиционирования `project_id:user_id` — все события пользователя в одной партиции,
  в порядке отправки (важно для воронок и сессий).
- 12 партиций — потолок параллелизма writer'ов (KEDA `maxReplicaCount = 12`).

## Последствия
+ Приём не зависит от доступности ClickHouse; Kafka хранит 7 дней — можно переиграть данные.
+ Приём и запись масштабируются независимо (HPA по CPU vs KEDA по lag).
− Eventual consistency: событие видно в аналитике через ~1–2 с.
− Ещё один stateful-компонент в эксплуатации.
