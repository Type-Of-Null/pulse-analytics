# ADR-0002: At-least-once доставка + идемпотентная запись вместо exactly-once

**Статус:** принято

## Контекст
Kafka transactions дают exactly-once только внутри Kafka; ClickHouse в транзакцию не входит.
Нужно гарантировать, что событие не потеряется и не задвоится при рестартах и ребалансах writer'а.

## Решение
1. Offset'ы коммитятся вручную и **только после** успешного INSERT в ClickHouse → ничего не теряется.
2. Повторная доставка того же батча отсекается `insert_deduplication_token`, который детерминированно
   считается из `topic/partition/offset`-диапазона батча (ClickHouse помнит последние токены).
3. Если батч пересобрался иначе (ребаланс), дубликаты схлопываются `ReplacingMergeTree`
   по ключу, включающему `event_id` (клиентский idempotency key) — и ретраи SDK не задваивают события.
4. При отзыве партиций (`on_partitions_revoked`) writer сбрасывает буфер и коммитит до передачи
   партиции другому consumer'у.
5. Невалидные сообщения уходят в DLQ (`events.dlq`) с заголовками-причинами, а не блокируют партицию.
6. Ошибки ClickHouse ретраятся с экспоненциальной задержкой; после исчерпания попыток процесс
   падает без коммита — Kubernetes перезапустит pod, данные перечитаются.

## Последствия
+ Эффективно exactly-once результат без распределённых транзакций.
− До фонового merge возможны дубли в «сырых» запросах; аналитические запросы используют
  `uniq`/`windowFunnel`, нечувствительные к дублям, а точные счётчики — `FINAL` при необходимости.
