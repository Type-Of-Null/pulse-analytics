# ADR-0003: Реестр API-ключей в памяти из compacted-топика

**Статус:** принято

## Контекст
Каждый запрос на приём событий нужно авторизовать по API-ключу. Ходить в Postgres на каждый
запрос — это лишняя задержка и связь «упал Postgres → упал приём».

## Решение
- Источник истины — Postgres (`admin-api`). Каждое изменение ключа пишет запись в таблицу `outbox`
  **в той же транзакции** (ADR-0004).
- `outbox-relay` публикует изменения в compacted-топик `projects.api-keys`:
  ключ сообщения — SHA-256 ключа, значение — `project_id`, отзыв — tombstone (`value = null`).
- Каждый pod `ingest-api` / `analytics-api` при старте вычитывает топик с начала до end offset'ов,
  зафиксированных на старте, и только потом отвечает `ready` (readiness probe держит pod вне
  балансировки). Дальше — tail в фоне.
- Сырые ключи нигде не хранятся: ни в Postgres, ни в Kafka — только хэши.

## Последствия
+ Авторизация — O(1) lookup в dict, без сети; Postgres может лежать, приём работает.
+ Compaction ограничивает размер топика числом живых ключей.
− Отзыв ключа применяется с задержкой ~1 с (outbox poll + доставка), это приемлемо.
− Память pod'а растёт с числом ключей (≈100 байт на ключ — миллионы ключей ок).
